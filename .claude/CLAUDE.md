# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository.

## What this is

Web version of **vLQMS**, a legacy Windows liquor-store ERP by Softvent (masters, purchase/sales, stock, DSR, reports): React SPA in `frontend/`, FastAPI backend in `backend/`. The legacy .NET source isn't available; both were rebuilt from legacy docs. `frontend/LEGACY_PARITY.md` maps every legacy screen to its status (Built / Partial / Stub / Missing) and lists gaps: read it before adding or extending a screen, update it when you close a gap. `backend/Rpts/` holds the legacy Crystal `.rpt` print formats, for reference.

## Commands

Backend, from `backend/`:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env          # JWT/SMTP settings; DB_* keys are written by the sign-in page's Database setup
.venv/bin/uvicorn app.main:app --reload --port 8001   # Swagger UI at http://localhost:8001/docs
.venv/bin/python -m pip install -r requirements-dev.txt && .venv/bin/python -m pytest   # API tests
```

Port matters: `frontend/vite.config.js` proxies `/api/*` to **:8001** (prefix stripped). uvicorn ignores `API_PORT` in `.env`, so pass `--port 8001`. `GET /` reports whether the DB is connected.

Frontend, from `frontend/`:

```bash
npm run dev      # Vite on :5173; calls backend at VITE_API_URL (frontend/.env), else /api → :8001
npm run build    # plain JS/JSX: no type-check step
npm run lint     # eslint (flat config: react-hooks, react-refresh)
npm test         # Vitest + RTL, watch mode; npm run test:run runs once
npm run dev:central   # central site page (central.html) on :5180, proxying /api → :8002
```

Central site (hosted, many shops), from `backend/`: `CENTRAL_DEMO=1 .venv/bin/python -m uvicorn app.central.main:app --port 8002` (in memory; prints a demo shop key and admin password). With a database, `tools/central.py` adds shops (prints the sync key once), users and grants. Hosting: `deploy/central/` (docker compose + Caddy) and its README.

**Tests.** Frontend: Vitest + RTL (jsdom), tests beside the component as `*.test.jsx` (example `components/common/DropdownMenu.test.jsx`); `vitest.config.js` reuses `vite.config.js`; `src/test/setup.js` loads jest-dom. Backend: pytest in `backend/tests/` (`pytest.ini`, asyncio auto mode), calling the app in-process via httpx `AsyncClient` + `ASGITransport` on sample data (`tests/sample_data.py`, installed once by `tests/seed.py` from `conftest.py`; DB settings blanked, startup event doesn't run). `conftest.py` restores the in-memory store after each test and enables respx so no real outgoing HTTP happens. Doc numbers keep counting across tests: assert on pattern only. Check frontend changes with `npm run test:run`, `npm run build`, `npm run lint` (plain `.js`/`.jsx` since 2026-10-07: no TypeScript/`tsc`); backend with `pytest`, `/docs` or curl (password endpoints take only encrypted passwords: get a token with a script that encrypts like `tests/conftest.enc()`, or use the UI). With the backend down, API calls throw `ApiError` and the footer shows "API: offline".

**No sample data and no demo logins** (pytest has its own in `tests/seed.py`: `ADMIN`/`admin`, `GURU`/`guru` Manager, `PRADEEP`/`pradeep` and `RAVI`/`ravi` Cashier). Users are the shop's own (`MstUser`): each signs in once with the desktop password or the lowercase user code, which is then hashed (`_verify_password` in `app/routers/auth.py`). Role comes from the desktop role (`MstROLE`: code or name exactly ADMIN/ADMINISTRATOR… → Administrator; MANAGER…, or users `OFFICE`/`MANAGER` → Manager; else Cashier; `db_store._role_for`); only a role set in Admin Master (`role_set_in_web`) overrides it. The lowercase user code is never accepted as an Administrator's password. If no active user is an Administrator, the sign-in page asks for one (`components/auth/CreateAdmin.jsx` → `POST /setup/admin`, encrypted password, only while none exists). Sign-in needs the database: not set up → Database setup; offline → message and no form (503 from `/auth/login`).

**Testing aids (Administrator only).** Utilities → **About** shows the DB connection (no Disconnect button on the web; `/utilities/database/disconnect|reconnect`, `db.disconnect()`, `db.MANUAL_OFFLINE` remain for scripts; both POSTs are `CONTROL_PATHS` in `main.py`). No test-data mode and no sample data in the app: it always uses the shop's database. **Dashboard panels** can be hidden per role in Admin Master → Field rights → Dashboard (`security.DASHBOARD_PANELS`; Hidden only); the server refuses (403) only `/reports/restock` and `/reports/stock-movement` for a role whose panel is hidden; other panels use ordinary reports under the role's report rights.

## Backend architecture

- **Many shops, the desktop's way**: each shop runs its own backend beside its own SQL Server (works offline); Web Sync pushes daily summaries to the hosted central site (`app/central/`, :8002) and never blocks billing. Details: `docs/architecture/web-sync-central.md`.
- **One database: the shop's own SQL Server, the one the desktop vLQMS uses. No SQLite, no copy.** The web app reads and **writes the desktop's own tables directly** (back the DB up before first use). `app/store.py` holds all tables as module-level dicts, empty until `app/boot.py` loads them. DB credentials come from the one-time Database setup (sign-in page) and live only in `.env` (password sealed). `db.py` shares one connection under `_db_lock`: use `db.fetchall`/`db.execute`/`db.transaction()`.
- **Every change is saved to SQL Server in the same request** (`app/sqlstore.py`, one transaction; failure → 503 + reload). **A new write must call `store.touch(TABLE, key)` for any master/user/role row, and new documents must live in `store.DOCS`, or it is not saved.** Saves with an `Idempotency-Key` header are answered from `store.IDEMPOTENT`. Full detail (setup flow, table mapping, stock replay, merge): `docs/architecture/db-and-save.md`.
- **Simple masters from one description** (`app/master_specs.py`, pure data): Supplier Group, Customer Group, State, Currency, Location, Tax, Bank, Holiday live in the desktop's tables (`MstSUPPGROUP`, `MstCUSTGROUP`, `MstSTATE`, `MstCUR`, `MstLOC`, `MstTAX`, `MstBANK`, `MstHoliday`; the web creates no table). From each spec `store.py` makes the dict, `schemas.SIMPLE_MODELS` the model, `masters.py` the `/masters/<path>` CRUD, `db_store.load_simple_masters()` the loader, `sqlstore.LEGACY_MASTERS` the saver, `security` the field list; frontend side is `lib/simpleMasters.js` (sidebar, rights matrix, search, Field Rights, `App.jsx`). A new such master = one entry in each of the two files. Also built from the desktop menu: Bulk Master Update (`POST /masters/items/bulk-update`, `components/utilities/BulkMasterUpdate.jsx`), Label Printing (`components/utilities/LabelPrinting.jsx`, `lib/code128.js`, Code 128 via browser), and the Package-wise Sales / Purchase, Loyalty and Excise Stock reports (`routers/reports.py`, `reportDefs.js`). The licence key (`frmKeyReg`/`clsReg`) and the desktop's Exit item are deliberately not built.
- **Stock** changes only through `store.move_stock()`, which updates `ITEMS[code]["qoh"]` and appends to `MOVEMENTS` (read by Stock Ledger, Stock Balance, DSR). Any new stock-affecting transaction must use it. Anything taking stock out first checks the per-item total across all lines (`transactions._check_stock`), so stock can't go negative through the API. Item QOH is opening stock: set at item creation (logged as an `opening` movement), ignored on later edits. Masters in use (items on bills, groups with items, counters with bills, …) can't be deleted or re-coded (`masters.IN_USE`).
- **Documents** live in `store.DOCS[kind][doc_no]`. Numbers come from `next_doc_no(kind, prefix)`, like `26/<prefix>-0000001`. Each series starts at 1 (the sales invoice series continues after the highest `SINVNO` of the financial year already in `TrnHdrSINV`; year prefix from the company's financial year, `store.set_fin_year()`); held bills have their own `hold` series. Doc numbers contain `/`, so routes use `{doc_no:path}`.
- **`store.find()`** looks a master up by code or name (some React screens send names).
- **Routers** (`app/routers/`): `masters.py` (CRUD factory at `/masters/<path>`), `transactions.py` (list/get factory + one POST per document), `reports.py`, `tools.py` (SQL Query, Re Write Stock), `utilities.py` (Global Settings via `gsettings.py`, duplicate invoices, merge items, audit log via `admin_audit.record(...)`, About), `custom_reports.py`, `auth.py`, `company_files.py`; models in `app/schemas.py` (mirrored by the frontend's `masterConfigs.js`). Details: `docs/architecture/routers-and-utilities.md`.
- **Admin Master (Security)** (`app/security.py`, endpoints in `routers/auth.py`): rights come from the user's role via `security.modules_for(user)` / `rights_for_user(user)` (no per-user rights): use `auth.can_use`/`has_right`, never `store.ROLES` directly. `security.password_problem` applies Login Settings; `require_login` blocks everything but changing the password once expired; master saves go through `security.apply_field_rights`/`hide_fields` (Field Level Rights) and `mark_approval` (Master Approvals; documents call `security.check_authorised`); Customised Reports check `security.can_run_report`; destructive utilities call `security.check_admin_password(user, body.admin_password)` (additional ADMIN password, or the caller's own). A new master needs its path in `security.TABLES`/`APPROVABLE`/`master_fields`.
- **Credentials from the UI are encrypted when the browser can** (owner's decision: plain `http://` on the LAN is fine, so a browser without WebCrypto sends the password as typed and `secure_fields.REQUIRE_ENCRYPTED` is off). The browser encrypts every password field with the server's RSA key (`frontend/src/lib/secureField.js` → `encryptSecret(value, purpose)`; key and server time from public `GET /auth/transport-key`; RSA-OAEP-256 with the field's purpose and a server-clock timestamp); the backend decrypts with `secure_fields.decrypt(value, purpose)`, refusing plain, stale (5 min), re-used or other-field values. A new screen/endpoint with a password field must do the same. Secrets the server must read back (e.g. a DB password saved from the UI) are sealed with `secure_fields.seal()/unseal()` (AES-256-GCM). Keys are in `backend/data/` (`transport_key.pem`, `secret.key`, 0600, gitignored; `VLQMS_KEYS_IN_MEMORY` keeps them in memory, as in tests). Losing `secret.key` means the sealed DB password can't be read: rerun Database setup. WebCrypto needs HTTPS or localhost. Tests encrypt with `conftest.enc()`.
- **Auth:** `POST /auth/login` returns a JWT (HS256, 24 h, secret from `JWT_SECRET`/`SECRET_KEY`). Every endpoint needs `Authorization: Bearer <token>`: `main.py` applies `auth.require_login` app-wide; only `auth.PUBLIC_ROUTES` are open (health `/`, login, `GET /masters/company` for the sign-in page, company file content (`<img>` tags load it without a token), and `/setup/*`, open until the DB is in use, then it checks for an Administrator itself). A new public endpoint must be added there. The `X-User` header is no longer trusted. Use `Depends(get_current_user)` / `Depends(require_admin)`, never call them directly. Every write endpoint also needs `Depends(require_module("<module name>", ...))` (403 otherwise), using the same module names as `store.ROLES` and the sidebar. Reads need only a login, except Profit Margin and Customised Reports. Passwords are salted PBKDF2-SHA256 (`app/passwords.py`, 600k rounds; `PASSWORD_HASH_ITERATIONS` lowered only in tests); `MstUser` users are hashed on first login. New passwords need 8+ characters mixing letters with numbers or symbols. Five wrong passwords lock a user name for 15 minutes (429). Tokens carry a password version (`pwv`), so a password change or deactivation signs the user out. `JWT_ALGORITHM` and `JWT_EXPIRATION_HOURS` in `.env` are not read.
- **Doc Designer** (`app/designer.py`, `app/schema_meta.py`): the desktop's designer tables drive print options and master screens (definition via `GET /designer/screen/{id}`; frontend `lib/designerStore.js`, `lib/designerFields.js`, `hooks/useScreenFields.js`); formulas run in `app/formulas.py` + `lib/formulas.js`. Sales Invoice / Purchase Bill screens, Expense and vouchers are not yet driven by it. Details, programme status and legacy source paths: `docs/architecture/doc-designer.md` (read before changing print or designer behaviour).
- **Shop opening hours and map** (Dashboard store banner's Store Open / Closed chip, `hooks/useShopHours.js` → `GET /company/hours`, `app/shop_hours.py`): no Google API or key. Karnataka retail liquor timings (10:00 AM to 10:00 PM India time, every day; `SHOP_OPEN_TIME` / `SHOP_CLOSE_TIME` in `.env` change them); closed on dates in Holiday Master (`MstHoliday`, `store.HOLIDAYS`), worked out per request. The Company Master map is the Google Maps embed the owner pastes (`COMPANY.map_embed`, an `<iframe>` or its link; `schemas.Company` keeps only the `src` and accepts only Google Maps links); with none pasted, a frame searching the company address is shown.
- **CORS allows every origin** (`allow_origins=["*"]`, any method/header; `main.py`) because the frontend calls the backend directly at its `VITE_API_URL` from another address. The API uses Bearer tokens, never cookies, so no credentials are involved. No `CORS_ORIGINS` setting. Not needed when the backend serves `frontend/dist` itself (same origin; `/docs`, `/redoc`, `/openapi.json` stay the API's).

## Frontend architecture (`frontend/src`)

Every source file starts with a header comment saying what it does. Layout:

```
App.jsx, main.jsx     app shell + screen switch, entry point
central/              hosted central site (central.html → central/main.jsx): CentralApp, CentralLogin, ChangePassword,
                      ShopDashboard (one or all shops' day), StockLookup, Indents, SyncStatus; reuses lib/ and components/common
lib/                  non-UI code: api.js (only backend client), modules.js (module registry, canOpen),
                      styles.js (shared Tailwind classes, money()), csv.js, xlsExport.js, formatters.js, utils.js
hooks/                useCompanyProfile.js
data/                 stockData.js (live item catalogue for Sales Invoice / Purchase Bill), salesCounters.js (invoice types + constants)
constants/images.js   bundled images, productImage()
components/
  common/             Modal, ConfirmDialog (useConfirm), DropdownMenu, Toast + toastStore, FormField, FormErrorSummary, KeyboardShortcutsModal
  layout/             Sidebar, ModuleSearch, VlqmsLogo
  auth/               Login
  dashboard/          Dashboard
  admin/              AdminMaster (+ AdminUsersTab, PermissionMatrixTable, matrixDefs)
  masters/            MasterCrud engine + masterConfigs, Masters (simple masters), Item/Company/Supplier/Sales Counter/Price List screens
  transactions/       SalesInvoice (+ Setup, Dialogs), PurchaseBill/, ItemLinesEntry + StockTransactions, Expense, Closing Stock, Cash Denomination
  reports/            reportDefs + ApiReport + ReportShell, DailySummaryReport, StockBalanceReport, ReportsDashboard (Customised Reports)
  print/              rptRegistry, PrintFormatSelectorModal, layouts/ (one per printer format)
  ui/                 third-party components (charts, loader); don't restyle app screens with these
```

Put a new screen in the folder for its sidebar group; shared non-UI code goes in `lib/`.

- **No router library, but every screen has its own URL.** `App.jsx` keeps the active module name in `activeTab`; `renderContent()` switches on it. `lib/routes.js` maps module name ↔ path (`/sales-invoice`, `/item-master`, … Dashboard `/`, Admin Master `/adminMaster`) and App syncs the address via History API pushState/popstate. Sidebar items are real `<a href>` links, so a screen opens in another tab (the new tab gets its sign-in token from open tabs via a BroadcastChannel in `lib/api.js`). After login the app opens the screen the address names if the role may open it, else the Dashboard. A new module needs no route code (path is made from its name). To add a screen: add its name to `MODULE_GROUPS` in `src/lib/modules.js` (feeds sidebar, module search, role rights), add search words to `MODULE_KEYWORDS`, add a `case` in `App.jsx`.
- **Module names are keys.** The same string is used for routing, the sidebar, and per-role rights in `backend/app/store.py` `ROLES`. Renaming a module means changing both.
- **Field rules and mandatory fields** come from the desktop's Doc Designer (`UtlDocDsgrFlds`: `FldBlnMandatory`, type, width; read it with a SELECT to check a screen against the desktop). Typed values are checked by `backend/app/validation.py` (requests only, never listing), mirrored in `frontend/src/lib/validation.js`: mobile/phone 10 digits, PIN 6, GSTIN, PAN, HSN, IFSC, MICR, account no., e-mail, tax % 0 to 100; boxes keep only allowed characters. Mandatory beyond name/code: Item MRP, Package, UOM, group, Liquor Category; Supplier GSTIN; Tax Type; Bank Display Name; Ledger Group; Package litres. Not built yet: Customer GSTIN and Currency (mandatory in the desktop), Sales Invoice Location.
- **E-mail (SMTP) settings** are typed on the sign-in page's Database & report settings and in Print Settings (`components/common/SmtpSetting.jsx` → `/setup/smtp`, `/setup/smtp/test`, same access as DB settings): written to `SMTP_*` in `.env`, password encrypted in the browser (purpose `smtp`) and kept only sealed as `SMTP_PASSWORD_ENC` (`mailer.password()`); a blank server turns e-mail off.
- **Windows-style layout.** The sidebar is a collapsible tree (`NAV_TREE` in `lib/modules.js`: Inventory > Masters > Item Related …; a module missing from it shows under "More"). `MasterCrud` puts record details left and the list right, and draws fields with the same `section` (`masterConfigs.js`) in a `common/GroupBox`. Item pickers use `transactions/ItemPickGrid` (ItemCode / ShortName / HotKey / ItemName): the Sales Invoice search lists only in-stock items and opens on a click; the Purchase Bill's F4 "Add Item Into Purchase Bill" window lists liquor items only (cases × bottles per case = total bottles), and items can be entered only after the supplier and the invoice (PB) value.
- **Auth.** `Login` returns an `ApiUser` with `role`, `modules` and a JWT. `canOpen()` gates screens (`'*'` = Administrator = everything). `setAuthUser(user, role, token)` stores the token in `sessionStorage` (`vlqms_jwt_token`: survives refresh, not closing the tab); every request sends `Authorization: Bearer <token>`. On load `App.jsx` restores the session from `/auth/me` (and last screen), re-checks every minute and on window focus; any 401 returns to sign-in with the reason. `setAuthRights(modules, rights)` feeds `canDo(module, 'add'|'edit'|'delete')` and `canSeeCost()`, used to hide buttons and cost fields (the backend enforces the same: `require_right`, `hides_cost`). Users change their own password from the header key button (`POST /auth/change-password`).
- **Admin Master** (`AdminMaster.jsx`, `AdminUsersTab.jsx`, `PermissionMatrixTable.jsx`, screen list in `matrixDefs.js`) shows Open/Add/Edit/Delete ticks per screen, but only module names are saved (`PUT /admin/roles/{name}` with `{name, modules}`); Add/Edit/Delete ticks aren't stored. When adding a module, also add it to `MATRIX_SCREENS`.
- **API client: `src/lib/api.js` is the only file that talks to the backend.** It holds the backend address (`VITE_API_URL` in `frontend/.env`, e.g. `http://localhost:8001`; without it calls go to `/api/<path>` on the page's address, which Vite proxies; `VITE_CENTRAL_API_URL` for the central site), the session, **one named exported function per endpoint** (`getItems()`, `saveSalesInvoice(body, key)`, `createMaster(path, body)`, `getDsr(on)`, `companyFileUrl(id)`, …) and response shapes (snake_case as FastAPI returns; described in comments, not types, since the 2026-10-07 JS conversion). Screens import these functions and never build URLs or call `fetch`; the generic `request()` is private. A new endpoint gets a new function (grouped by router) and its test mocks that function or `fetch`. Helpers: `errorText`, `qs`, `todayIso`, `newIdempotencyKey`. Error messages come from FastAPI's `detail`.
- **Reusable screen engines** (mirror the legacy generic forms):
  - `MasterCrud.jsx` + field lists in `masterConfigs.js` → simple masters at `/masters/<path>`. Field lists mirror `backend/app/schemas.py`: change both together. `Masters.jsx` wires them.
  - `reports/reportDefs.js` (`REPORTS` map: endpoint, filters, columns) rendered by `reports/ApiReport.jsx` and `ReportShell.jsx`. `App.jsx` checks `REPORTS[activeTab]` before its switch, so a simple report needs only a new entry.
  - `ItemLinesEntry.jsx` is the shared item-line grid of the stock transactions (`StockTransactions.jsx`: Purchase Indent, Stock Deduction, Sales Return).
  - `print/`: **documents print through their original Crystal `.rpt` files**; the backend only builds a job and calls a print service over HTTP (real Crystal bridge on Windows, else built-in `app/mock_bridge.py`). **Report prints (DSR, Stock Balance, Customised Reports) still use the old `PrintFormatSelectorModal.jsx` / `rptRegistry.js` / `layouts/*`, which are not derived from the `.rpt` files** (don't describe them as matching legacy prints). A new format needs a `mock_bridge.py` template. Details: `docs/architecture/printing.md`.
- **Sales Invoice has two steps.** `SalesInvoiceSetup` (counter, invoice no, payment type, customer) then `SalesInvoice`. `App.jsx` holds the draft state (`invoiceDraft`, `billOpen`). Saving a Sales Counter Master opens the setup form.
- **Dashboard** (`components/dashboard/Dashboard.jsx`) reads `/reports/dsr`, `/reports/sales/daily` (last 7 days), `/reports/stock-movement` and the first company image. `ModuleSearch.jsx` (⌘K or `/`) searches module names and `MODULE_KEYWORDS`; `KeyboardShortcutsModal.jsx` (`?`) lists shortcuts.
- **Keyboard first.** Billing runs from the keyboard: `lib/keys.js` (`useShortcuts`, `enterMovesNext`, `focusField`), `common/useDialogKeys.js` (every dialog), `common/Kbd.jsx` (key hints on buttons), `transactions/ItemSearchBox.jsx` + `data/itemSearch.js` (bill item search). Keys are listed in `.claude/rules/popups-and-errors.md` §4 and the Shortcuts sheet; a new screen or dialog must work without a mouse.
- **Notifications and validation** follow `.claude/rules/popups-and-errors.md`: server results go to the snackbar (`Toast.jsx` / `toastStore.js`); client-side form mistakes show inline (`FormField.jsx`, `InlineError`/`FormErrorSummary` in `FormErrorSummary.jsx`), never as toasts.
- Sales Invoice and Purchase Bill take items from `data/stockData.js` (`useStockItems()`, loaded from `/masters/items`). A bill line holds the item's index in `STOCK_ITEMS`, so that array is only merged in place, never reordered. Call `loadStockItems()` after a save to refresh QOH. No sample data in the frontend either: counters, customers and sales persons come from the API, the next bill number from `GET /transactions/next-number` (a preview; the backend numbers on save), and prints show only real data (`print/printData.js` holds empty shapes; Print is disabled when there is nothing to print).
- Styling notes (Tailwind v4, palette, shared class strings in `lib/styles.js`) are in `frontend/CLAUDE.md`.

## Workflow

- **Never commit credentials.** DB host/IP, port, user, password, the legacy encrypted password, and JWT secrets go only in `backend/.env` (gitignored). Code gets no defaults for them; `.env.example` and docs get placeholders only. `SvtConn.ini` is gitignored for the same reason. Before a commit, grep the diff for IPs and passwords.
- After changing a screen, endpoint or report, run the `parity-reviewer` agent.

## Reverse-engineering skills (CLysis)

CLysis skills (https://github.com/t-hasuike/CLysis, MIT; plugins `legacy-investigation` and `legacy-analysis`, copied into `.claude/skills/` and `.claude/commands/`) are installed for studying the legacy desktop vLQMS: `/project-guide`, `/current-spec`, `/change-impact`, `/current-legacy`, `/current-distortion`, `/legacy-decode`, `/deep-dive`, `/understand`, `/investigate-flow`, `/bug-hunt`. They only read and document: use them to learn how a legacy screen, report or table behaves, then build it here. **Never change the web app's existing UI styles because of them**: new screens reuse the current look (`lib/styles.js`, Tailwind palette, existing components); the skills inform behaviour and data, not appearance. Write findings under `docs/legacy-analysis/`, not in the source tree.
