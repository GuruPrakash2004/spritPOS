# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A web version of **vLQMS**, a legacy Windows liquor-store ERP by Softvent (masters, purchase/sales transactions, stock, DSR and reports). It has two parts: a React SPA in `frontend/` and a FastAPI backend in `backend/`. The legacy .NET source isn't available, so both were rebuilt from the legacy docs. `frontend/LEGACY_PARITY.md` maps every legacy screen to its status here (Built / Partial / Stub / Missing) and lists the gaps. Read it before adding or extending a screen, and update it when you close a gap. `backend/Rpts/` holds the legacy Crystal `.rpt` print formats the app uses, for reference.

## Commands

Backend, from `backend/`:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env          # JWT/SMTP settings; the DB_* keys are written by the sign-in page's Database setup
.venv/bin/uvicorn app.main:app --reload --port 8001   # Swagger UI at http://localhost:8001/docs
.venv/bin/python -m pip install -r requirements-dev.txt && .venv/bin/python -m pytest   # API tests
```

The port matters: `frontend/vite.config.ts` proxies `/api/*` to **:8001** (prefix stripped). uvicorn does not read `API_PORT` from `.env`, so pass `--port 8001` yourself. `GET /` reports whether the DB is connected.

Frontend, from `frontend/`:

```bash
npm run dev      # Vite on :5173; the app calls the backend at VITE_API_URL (frontend/.env), else /api → :8001
npm run build    # tsc -b (type-check) then vite build
npm run lint     # eslint (flat config: typescript-eslint, react-hooks, react-refresh)
npm test         # Vitest + React Testing Library in watch mode; npm run test:run runs once
npm run dev:central   # the central site's page (central.html) on :5180, proxying /api → :8002
```

Central site (hosted, many shops), from `backend/`: `CENTRAL_DEMO=1 .venv/bin/python -m uvicorn app.central.main:app --port 8002` (in memory, prints a demo shop key and admin password); with a database, `tools/central.py` adds shops (prints the sync key once), users and grants. Hosting: `deploy/central/` (docker compose + Caddy) and its README.

The frontend has Vitest + React Testing Library (jsdom). Tests sit next to the component as `*.test.tsx` (example: `components/common/DropdownMenu.test.tsx`); `vitest.config.ts` reuses `vite.config.ts`, and `src/test/setup.ts` loads the jest-dom matchers. The backend has pytest tests in `backend/tests/` (settings in `pytest.ini`, pytest-asyncio auto mode): they call the app in-process with an httpx `AsyncClient` over `ASGITransport`, always on the sample data (`tests/sample_data.py`, installed once by `tests/seed.py` from `conftest.py` with the demo users and company; the DB settings are blanked there, and the startup event doesn't run), and `conftest.py` restores the in-memory store after every test and switches respx on so no test can make a real outgoing HTTP call. Doc numbers keep counting across tests, so assert on their pattern only. Check frontend changes with `npm run test:run`, `npm run build` and `npm run lint`, and backend changes with `pytest`, `/docs` or curl (login and other password endpoints only take encrypted passwords, so get a token with a script that encrypts like `tests/conftest.enc()`, or use the UI). When the backend isn't running, the frontend's API calls throw `ApiError` and the footer shows "API: offline".

**No sample data and no demo logins** (the pytest suite has its own, in `tests/seed.py`). The users are the shop's own (`MstUser`): each signs in with their desktop password or the lowercase user code once, which is then hashed (`_verify_password` in `app/routers/auth.py`). Their role comes from the desktop role (`MstROLE`: role code or name exactly ADMIN/ADMINISTRATOR… → Administrator; MANAGER…, or users `OFFICE`/`MANAGER` → Manager; else Cashier; `db_store._role_for`), and only a role set in Admin Master (`role_set_in_web`) overrides it; the lowercase user code is never accepted as an Administrator's password. If no active user is an Administrator, the sign-in page asks for one (`components/auth/CreateAdmin.tsx` → `POST /setup/admin`, encrypted password, only while there is none). Sign-in needs the database: not set up → Database setup; offline → a message and no form (503 from `/auth/login`). The tests' users are in `tests/seed.py` (`ADMIN`/`admin`, `GURU`/`guru` Manager, `PRADEEP`/`pradeep` and `RAVI`/`ravi` Cashier).

**Testing aids (Administrator only).** Utilities → **About** shows the database connection and has **Disconnect / Reconnect database** (`/utilities/database/disconnect|reconnect`, `db.disconnect()` sets `db.MANUAL_OFFLINE` so nothing reconnects by itself). Both POSTs are `CONTROL_PATHS` in `main.py`: serialised, never refused as "database offline", nothing saved after them. There is **no test-data mode and no sample data in the app**: it always works on the shop's own database. **Dashboard panels** can be hidden per role in Admin Master → Field rights → Dashboard (`security.DASHBOARD_PANELS`; Hidden only); only `/reports/restock` and `/reports/stock-movement` are refused (403) by the server for a role whose panel is hidden; the other panels use ordinary reports that stay open to the role's report rights. Disconnecting is logged (server log), not in the ADMIN Audit Log.

## Backend architecture

- **Many shops, the desktop's way.** Each shop runs its own backend (`app.main`) next to its own SQL Server, so billing works without internet; the backend can also serve the built frontend (`frontend/dist`, API under `/api` too, `SERVE_FRONTEND=0` turns it off). **Web Sync** (`app/websync.py`, Utilities → Web Sync, legacy `frmModWebSync`) pushes each day's summary in the desktop's central-table shape (`RptDSRSmry`, `RptDSRCtrSales`, … `RptFastMov`, `RptMinStk`, `TrnHdrPI`/`TrnDtlPI`) and the stock (`RptWebStk`) over HTTPS to the hosted **central site** (`app/central/`, a separate FastAPI app on :8002), with a per-shop Bearer key (`WEB_SYNC_URL`/`WEB_SYNC_KEY` in `.env` only). It never sends an unloaded (empty) store (`sqlstore.enabled()`), starts after the history load, catches up missed days and never blocks billing (`/utilities/web-sync` is in `NOT_WRITES`). The central site replaces a shop's rows per day; its tables are listed once in `app/central/tables.py` (validation, SQL, and `migrations/central/001_central.sql`, checked by `tests/test_central.py`); storage is `central/repo.py` (`SqlRepo` on `CENTRAL_DB_*`, never the shop's `DB_*`; `MemoryRepo` without a database). Owners (`CenUser`, role Admin/Owner) sign in with encrypted passwords, change a temporary one first, and see only granted shops (`CenUserClient`).

- **One database: the shop's own Microsoft SQL Server, the one the desktop vLQMS uses. No SQLite, no copy of the data.** The backend runs on the client's PC/server next to their local SQL Server (often SQL Server Express) and works on the desktop's **own tables directly** (`MstITEM`, `MstCUST`, `TrnHdrSINV`, `UtlStockList`, ...), so the desktop app and the web app always share the same data. `app/store.py` holds every table as a module-level dict (`ITEMS`, `CUSTOMERS`, `USERS`, `ROLES`, `SETTINGS`, `DOCS`, …), **empty until loaded** (only built-in config: roles, Global Settings definitions). On startup `app/boot.py` connects (`app/db.py`: pyodbc with ODBC Driver 18/17, then pymssql; `DB_HOST` may be `localhost\SQLEXPRESS`, `DB_PORT` optional, SQL login only, the password sealed in `DB_PASSWORD_ENC`) and, once the database is set up, `db_store.load_masters()` loads the live data from the desktop tables (company, financial years, items, customers, suppliers, groups, brands, UOMs, packages, ledger groups, ledgers, sales counters, sales persons, last purchase dates, users) and `load_transactions()` the latest 200 sales invoices and 100 purchase bills in a background thread; then `sqlstore.load()` lays the web app's own saved data over it. **One-time Database setup** (`app/setup_db.py`, `routers/setup.py`, `components/auth/DatabaseSetup.tsx`): while `.env` has no database, the sign-in page shows Database setup instead of the login form. It is open to anyone who reaches the sign-in page while the database isn't set up (there is no setup code; a sealed password this PC can't unseal counts as not set up, `db._password_unreadable`); otherwise only an Administrator can use `/setup/*` (Global Settings → Database changes the settings in use; a blank password keeps the saved one); the one exception is a set-up database that is offline, when the sign-in page's Database settings also works from the server PC itself (a loopback request), because nobody can sign in then. It tests the server, lists its databases, saves the connection (`app/envfile.py` writes only the `DB_*` keys, atomically; the password arrives encrypted for purpose `db` and is stored sealed), checks the database is a vLQMS one (`setup_db.REQUIRED_TABLES`, and the desktop's stock trigger on `UtlStockList`), creates the web app's **five own tables** `Web_AppRow`/`Web_AppDoc`/`Web_AppMove`/`Web_AppSetting`/`Web_ToolAudit` from `migrations/web_app_tables.sql` (guarded; no desktop table is created, altered or emptied) and loads the data. **Nothing is copied.** The web app **writes to the live desktop tables**, so back the database up before first use. Without a database the app has no data and nobody can sign in; the pytest suite installs `tests/sample_data.py` (through `tests/seed.py`). `pyodbc` is only installed off macOS (see `requirements.txt`), so on a Mac the connection goes through pymssql (SQL logins only).

- **One DB connection, serialised.** `db.py` shares a single connection between request threads and the background loader, so every query runs under `_db_lock` (pymssql fails with "Unknown error" on concurrent use). Keep new DB calls going through `db.fetchall`/`db.execute`, or `db.transaction()` for several statements that must commit together (it uses `?` placeholders for both drivers).
- **Every change is saved to SQL Server in the same request** (`app/sqlstore.py`). After a successful POST/PUT/DELETE the write middleware in `main.py` (which also runs writes one at a time) calls `sqlstore.save()`, which writes what changed since the last save in ONE `db.transaction()`: rows marked with `store.touch(TABLE, key)` go to the desktop's own table (`LEGACY_MASTERS`: `MstITEM`, `MstCUST`, `MstSUPP`, `MstITEMGROUP`, `MstBrand`, `MstUOM`, `MstPKG`, `MstUser`, `MstLed`, `MstLedgroup`, `MstSC`, `MstSP`; new rows get `MAX(ID)+1`; a user's desktop `LoginPwd` is never touched) and whole to `Web_AppRow` (fields with no desktop column, e.g. password hashes; other masters, roles and rights live only there); documents without an `origin` go whole to `Web_AppDoc`, and saved sales invoices / purchase bills also to `TrnHdrSINV`/`TrnDtlSINV` and `TrnHdrPB`/`TrnDtlPB` (cancel/remove set `Cancelled`/`IsDelete`, also on bills made in the desktop); `MOVEMENTS[APP_MOVEMENTS_FROM:]` go to `Web_AppMove` (the web's ledger) and each to a `UtlStockList` row, whose desktop trigger keeps `TrnQOH` (a sale cancel deletes that bill's stock rows, as the desktop does); settings and other web state to `Web_AppSetting`; audit entries to `UtlAdmAudit`/`UtlAdmAuditItem` (the desktop's own audit tables, so the desktop's history shows too). If the transaction fails the request answers **503** and `sqlstore.reload()` reloads memory from SQL Server, so memory never keeps an unsaved change. At startup item QOH comes from `TrnQOH` (which includes the web's moves); `sqlstore.load()` takes the web moves off and replays them so `store.BASE_QOH` stays right for Re Write Stock, and moves the invoice series past the highest `SINVNO`. **A new write must call `store.touch()`** for any master/user/role row it changes, and new documents must live in `store.DOCS`, or the change is not saved. Merge Items calls `sqlstore.merged(src, dst)`, which re-points every table's ITEMID and adds the two `TrnQOH` rows. Saves sent with an `Idempotency-Key` header (Sales Invoice and Purchase Bill send one per draft) are answered from `store.IDEMPOTENT` when repeated with the same body (a different body gets 409), so a double-click makes one bill. Uploaded company files are kept on disk in `backend/uploads/company/`.
- **Stock** is changed only through `store.move_stock()`. It updates `ITEMS[code]["qoh"]` and appends to `MOVEMENTS`, which the Stock Ledger, Stock Balance and DSR reports read. A new stock-affecting transaction must go through it. Anything that takes stock out checks the total per item across all lines first (`transactions._check_stock`), so stock can't go negative through the API. Item QOH is opening stock: set when an item is created (logged as an `opening` movement) and ignored on later edits. Masters in use (items on bills, groups with items, counters with bills, …) can't be deleted or re-coded (`masters.IN_USE`).
- **Documents** are kept in `store.DOCS[kind][doc_no]`. Numbers come from `next_doc_no(kind, prefix)` and look like `26/<prefix>-0000001`. Each series starts at 1 (the sales invoice series continues after the highest `SINVNO` of the financial year already in `TrnHdrSINV`; the year prefix comes from the company's financial year, `store.set_fin_year()`), and held bills have their own `hold` series. Doc numbers contain `/`, so routes use `{doc_no:path}`.
- **`store.find()`** looks a master up by code or by name, because some React screens send names.
- **Routers** (`app/routers/`): `masters.py` builds every master's CRUD at `/masters/<path>` from one `crud()` factory; `transactions.py` has a similar list/get factory plus one POST per document type; `reports.py` holds the report endpoints (`/reports/*`); `tools.py` holds the desktop TOOLS menu (`/tools/*`): SQL Query Execution (Administrator only; `_check_sql` allows one statement: SELECT anywhere; INSERT/UPDATE/DELETE only on `dbo.Web_*` tables that are not the web app's own records (`db.write_statement`), so in practice it only reads and the desktop's tables are never changed by hand-typed SQL, reads go through `db.read_only()`, which always rolls back; a change made here reaches the screens after a restart (memory is loaded at startup); every run is written to `Web_ToolAudit`) and Re Write Stock (`app/stock_rewrite.py`: checks documents against `MOVEMENTS[APP_MOVEMENTS_FROM:]` and QOH against `store.BASE_QOH` + those movements, and rebuilds them; set `APP_MOVEMENTS_FROM` and `BASE_QOH` only through `store.mark_app_start()`); `utilities.py` holds the desktop UTILITIES menu (`/utilities/*`, built phase by phase): Global Settings (rows in `store.GSETTINGS`, managed by `app/gsettings.py`: only settings the web app acts on, each with its `effect`; read them with `gsettings.yes()/number()/value()`, and `gsettings.check_not_frozen()` for `FreezeDate`; `GET /settings/values` gives them to the screens; the older `store.SETTINGS` is kept in step), Remove Duplicate Invoice (`app/duplicate_invoices.py`: web bills only, stock back through `sale-cancel` moves, status `DELETED`), Merge Items / Replace and Remove Duplicate items (`app/item_merge.py`: moves lines, movements, QOH and base QOH to the kept item; `store.MERGED_ITEMS` maps old codes; `sqlstore.merged()` does the same in SQL Server), Compare Stock (sheets compared in the browser, `lib/stockSheet.ts`), the ADMIN Audit Log (`app/admin_audit.py`: call `admin_audit.record(screen, action, main_fld, earlier, changed, items)` in any endpoint that changes data; the write middleware keeps it only if the request succeeds and saves it with the request's changes in `UtlAdmAudit`/`UtlAdmAuditItem`, the desktop's own audit tables, so the desktop's history shows too; never record passwords) and About; `custom_reports.py` holds the Customised Reports, run first from the desktop's own definitions (`app/custom_engine.py` reads `UtlReportsCRHdr/CRTbl/CRDtl` and builds one SELECT per report; the built-in functions are the fallback; `app/rpt_custom.py` is ready to print the UDR ones through Crystal but none is offered yet) (and `POST /reports/custom/email`, which builds the .xls on the server and sends it through `app/mailer.py`, at most 10 per user per hour; SMTP settings only in `.env`); `auth.py` has login and the admin-only users and roles; `company_files.py` handles uploads. Pydantic models are in `app/schemas.py`, and the frontend's `masterConfigs.ts` field lists mirror them. `/settings` and `/sales-persons` live directly in `main.py`. `/reports/stock-movement` and `/reports/restock` feed the Dashboard. Restock is real time: it ranks items by sales speed over the last 15 days up to today, and with a DB connected it reads sales (`TrnHdrSINV`/`TrnDtlSINV`) and stock (`TrnQOH.CLBal`) live via `db_store.live_sales_and_stock()` (cached 20 s), adding this app's own movements since startup (`store.DB_BASE_MOVEMENTS`). Only items that actually sell can need restock. and `/reports/rpt-files` lists the `.rpt` files in `backend/Rpts/`, which holds only the 24 formats the app uses (listed in `rptRegistry.ts` and `list_rpt_files`). They are committed through the allow-list in `backend/.gitignore`, so they ship with the backend, except the 7 that embed the desktop app's SQL Server connection: those stay local and are copied to a host by hand.
- **Admin Master (Security)** (`app/security.py`, endpoints in `routers/auth.py`): rights come from the user's role through `security.modules_for(user)` / `rights_for_user(user)` (there are no per-user rights), so use `auth.can_use`/`has_right`, never `store.ROLES` directly; `security.password_problem` applies Login Settings; `require_login` blocks everything but changing the password once it has expired; master saves go through `security.apply_field_rights`/`hide_fields` (Field Level Rights) and `mark_approval` (Master Approvals; documents call `security.check_authorised`); Customised Reports check `security.can_run_report`; destructive utilities call `security.check_admin_password(user, body.admin_password)` (additional ADMIN password, or the caller's own). A new master needs its path in `security.TABLES`/`APPROVABLE`/`master_fields`.
- **Credentials from the UI are always encrypted** (owner's rule): the browser encrypts every password field with the server's RSA key (`frontend/src/lib/secureField.ts` → `encryptSecret(value, purpose)`, key and server time from the public `GET /auth/transport-key`, RSA-OAEP-256 with the field's purpose and a timestamp on the server's clock) and the backend decrypts it with `secure_fields.decrypt(value, purpose)`, refusing plain, stale (5 min), re-used or other-field values. A new screen or endpoint with a password field must do the same. Secrets the server must read back (e.g. a DB password saved from the UI) are sealed with `secure_fields.seal()/unseal()` (AES-256-GCM). Keys are in `backend/data/` (`transport_key.pem`, `secret.key`, 0600, gitignored; `VLQMS_KEYS_IN_MEMORY` keeps them in memory, as in the tests). Losing `secret.key` means the sealed DB password can't be read: run the Database setup again. WebCrypto needs HTTPS or localhost. Tests encrypt with `conftest.enc()`.
- **Auth:** `POST /auth/login` returns a JWT (HS256, 24 h, secret from `JWT_SECRET`/`SECRET_KEY`). Every endpoint needs `Authorization: Bearer <token>`: `main.py` applies `auth.require_login` to the whole app, and only `auth.PUBLIC_ROUTES` are open (health `/`, login, `GET /masters/company` for the sign-in page, company file content, which `<img>` tags load without a token, and `/setup/*`, which is open until the database is in use and then checks for an Administrator itself). A new public endpoint must be added there. The `X-User` header is no longer trusted. For the current user or an admin-only endpoint, use the dependencies `Depends(get_current_user)` / `Depends(require_admin)`; never call them directly. Every write endpoint also checks the caller's role with `Depends(require_module("<module name>", ...))` (403 otherwise), using the same module names as `store.ROLES` and the sidebar; a new write endpoint needs one. Reads need only a login, except Profit Margin and Customised Reports. Passwords are salted PBKDF2-SHA256 hashes (`app/passwords.py`, 600k rounds; `PASSWORD_HASH_ITERATIONS` is lowered only in the tests); `MstUser` users are hashed on their first login. New passwords need 8+ characters mixing letters with numbers or symbols. Five wrong passwords lock a user name for 15 minutes (429). Tokens carry a password version (`pwv`), so a password change or deactivation signs the user out. `JWT_ALGORITHM` and `JWT_EXPIRATION_HOURS` in `.env` are not read.
- **Doc Designer settings** (`app/designer.py`): the desktop's designer tables (`UtlTransactions`, `UtlOption`, `UtlOptionEmailDtls`, `UtlDocDsgrFlds`, `UtlMisc`) are read into `store.UTL_*` at start and by `POST /designer/refresh` (About → Refresh from Doc Designer), so print options follow the designer. Screen fields are loaded but the screens are still hand-built. The legacy VB.NET source is on `/Volumes/ClientData/Web/vlqms` (desktop) and the designer's in `/Volumes/ClientData/RepBak/vDocDesigner2020-*.vsvnbak` (a VisualSVN backup holding a zip); read them before changing print or designer behaviour.
- **Shop opening hours** (the Dashboard store banner's Store Open / Closed chip, `hooks/useShopHours.ts` → `GET /company/hours`, `app/shop_hours.py`): the shop is found on Google Maps (Places API (New) Text Search) by the company name + address from Company Master; its weekly hours are cached (`SHOP_HOURS_CACHE_HOURS`, default 6) and Open / Closed is worked out from them at every request in the shop's time zone. `GOOGLE_MAPS_API_KEY` lives only in `backend/.env` (never sent to the browser); without it the chip isn't shown. The shop is preferably the place picked on the map in Company Master (`components/masters/ShopPlacePicker.tsx`, Google's extended component library; `COMPANY.place_id`, read with Place Details); the map uses a separate, site-restricted browser key `VITE_GOOGLE_MAPS_BROWSER_KEY` in `frontend/.env.local` (see `frontend/.env.example`). The backend sends `Referrer-Policy: strict-origin` (origin only) because a site-restricted key needs it.
- **CORS allows every origin** (`allow_origins=["*"]`, any method and header; `main.py`), because the frontend calls the backend directly at its `VITE_API_URL` from another address. The API uses a Bearer token, never cookies, so no credentials are involved. There is no `CORS_ORIGINS` setting. Not needed when the backend serves `frontend/dist` itself (same origin; `/docs`, `/redoc` and `/openapi.json` stay the API's).

## Frontend architecture (`frontend/src`)

Folder layout. Every source file starts with a header comment that says what it does:

```
App.tsx, main.tsx     app shell + screen switch, entry point
central/              the hosted central site (central.html → central/main.tsx): CentralApp, CentralLogin, ChangePassword,
                      ShopDashboard (one or all shops' day), StockLookup, Indents, SyncStatus; reuses lib/ and components/common
lib/                  non-UI code: api.ts (the only backend client: address, session, one function per endpoint, response types), modules.ts (module registry, canOpen),
                      styles.ts (shared Tailwind classes, money()), csv.ts, xlsExport.ts, formatters.ts, utils.ts
hooks/                useCompanyProfile.ts
data/                 stockData.ts (live item catalogue for Sales Invoice / Purchase Bill), salesCounters.ts (invoice types + constants)
constants/images.ts   bundled images, productImage()
components/
  common/             Modal, ConfirmDialog (useConfirm), DropdownMenu (on-screen pop-up menus), Toast + toastStore, FormField, FormErrorSummary, KeyboardShortcutsModal
  layout/             Sidebar, ModuleSearch, VlqmsLogo
  auth/               Login
  dashboard/          Dashboard
  admin/              AdminMaster (+ AdminUsersTab, PermissionMatrixTable, matrixDefs)
  masters/            MasterCrud engine + masterConfigs, Masters (simple masters), Item/Company/Supplier/Sales Counter/Price List screens
  transactions/       SalesInvoice (+ Setup, Dialogs), PurchaseBill/, ItemLinesEntry + StockTransactions, Expense, Closing Stock, Cash Denomination
  reports/            reportDefs + ApiReport + ReportShell (table reports), DailySummaryReport, StockBalanceReport, ReportsDashboard (Customised Reports)
  print/              rptRegistry, PrintFormatSelectorModal, layouts/ (one per printer format)
  ui/                 third-party components (charts, loader); don't restyle app screens with these
```

Put a new screen in the folder for its sidebar group, and put shared non-UI code in `lib/`.

- **No router library, but every screen has its own URL.** `src/App.tsx` stores the active module name in `activeTab` state, and `renderContent()` switches on that string; `lib/routes.ts` maps module name ↔ path (`/sales-invoice`, `/item-master`, … Dashboard `/`, Admin Master `/adminMaster`) and App keeps the address in step with History API pushState/popstate. Sidebar items are real `<a href>` links so a screen can be opened in another browser tab (a new tab gets its sign-in token from the open tabs through a BroadcastChannel in `lib/api.ts`). After login the app opens the screen the address names if the role may open it, else the Dashboard. A new module needs no route code: its path is made from its name. To add a screen: add its name to `MODULE_GROUPS` in `src/lib/modules.ts` (this feeds the sidebar, the module search and role rights), add search words to `MODULE_KEYWORDS`, then add a `case` in `App.tsx`.
- **Module names are keys.** The same string is used for routing, in the sidebar, and in the per-role rights in `backend/app/store.py` `ROLES`. Renaming a module means changing both.
- **Auth.** `Login` returns an `ApiUser` with `role`, `modules` and a JWT. `canOpen()` gates the screens (`'*'` = Administrator = everything). `setAuthUser(user, role, token)` stores the token in `sessionStorage` (`vlqms_jwt_token`: survives a refresh, not closing the tab), and every request sends `Authorization: Bearer <token>`. On load `App.tsx` restores the session from `/auth/me` (and the last screen), re-checks it every minute and on window focus, and any 401 returns to the sign-in page with the reason. `setAuthRights(modules, rights)` feeds `canDo(module, 'add'|'edit'|'delete')` and `canSeeCost()`, which screens use to hide buttons and cost fields (the backend enforces the same: `require_right`, `hides_cost`). Users change their own password from the header key button (`POST /auth/change-password`).
- **Admin Master** (`AdminMaster.tsx`, `AdminUsersTab.tsx`, `PermissionMatrixTable.tsx`, screen list in `matrixDefs.ts`) shows Open/Add/Edit/Delete ticks per screen, but only the module names are saved (`PUT /admin/roles/{name}` with `{name, modules}`). The Add/Edit/Delete ticks are not stored. When you add a module, also add it to `MATRIX_SCREENS`.
- **API client: `src/lib/api.ts` is the only file that talks to the backend.** It holds the backend's address (`VITE_API_URL` in `frontend/.env`, e.g. `http://localhost:8001`; without it calls go to `/api/<path>` on the page's own address, which Vite proxies, and `VITE_CENTRAL_API_URL` for the hosted central site), the signed-in session, **one named exported function per backend endpoint** (`getItems()`, `saveSalesInvoice(body, key)`, `createMaster(path, body)`, `getDsr(on)`, `companyFileUrl(id)`, …) and the TypeScript shapes of the responses (snake_case, as FastAPI returns them). Screens import the functions they need and never build a URL or call `fetch` themselves; the generic `request()` is private. A new endpoint gets a new function in `api.ts` (grouped by router), and its test mocks that function or `fetch`. `errorText`, `qs`, `todayIso` and `newIdempotencyKey` are helpers there. Error messages come from FastAPI's `detail`. (It is TypeScript, not `.js`, so the 50-odd screens that use it stay type-checked.)
- **Reusable screen engines** (these mirror the legacy generic forms):
  - `MasterCrud.tsx` with field lists in `masterConfigs.ts` → the simple masters at `/masters/<path>`. Field lists mirror `backend/app/schemas.py`, so change both together. `Masters.tsx` wires them together.
  - `reports/reportDefs.ts` (`REPORTS` map: endpoint, filters, columns) rendered by `reports/ApiReport.tsx` and `ReportShell.tsx`. `App.tsx` checks `REPORTS[activeTab]` before its switch, so a simple report only needs a new entry here.
  - `ItemLinesEntry.tsx` is the shared item-line grid used by the stock transactions (`StockTransactions.tsx`: Purchase Indent, Stock Deduction, Sales Return).
  - `print/`: **documents print through their original Crystal `.rpt` files**, as the desktop does. `PrintDialog.tsx` + `lib/printing.ts` read the document's print options from `GET /print/options` (the Doc Designer's `UtlOption`: default option, click actions, after-save prompt; `backend/app/designer.py`) and ask `POST /print/render` for the PDF (each option also says whether its `.rpt` file is in the report folder, `available`, and the user's own last pick is kept on the server, `PUT /print/preference`, in `store.PRINT_PREFS`, which comes before the designer's default),, which `app/rpt_print.py` builds like `frmUtlReportViewer` (file, selection formula, parameters) and `app/rpt_bridge.py` has laid out by the Crystal Reports bridge (`backend/tools/rptbridge/`, Windows). Never draw a web copy of a `.rpt`. **Report prints (DSR, Stock Balance, Customised Reports) still use the old `PrintFormatSelectorModal.tsx` / `rptRegistry.ts` / `layouts/*`, which are not derived from the `.rpt` files** (don't describe them as matching the legacy prints); they are to move to the bridge (see `LEGACY_PARITY.md`).
- **Sales Invoice has two steps.** `SalesInvoiceSetup` (counter, invoice no, payment type, customer) comes first, then `SalesInvoice`. `App.tsx` holds the draft state (`invoiceDraft`, `billOpen`). Saving a Sales Counter Master opens the setup form.
- **Dashboard** is `Dashboard` in `components/dashboard/Dashboard.tsx`. It reads `/reports/dsr`, `/reports/sales/daily` (last 7 days), `/reports/stock-movement` and the first company image. `ModuleSearch.tsx` (⌘K or `/`) searches module names and `MODULE_KEYWORDS`, and `KeyboardShortcutsModal.tsx` (`?`) lists the shortcuts.
- **Keyboard first.** Billing is run from the keyboard: `lib/keys.ts` (`useShortcuts`, `enterMovesNext`, `focusField`), `common/useDialogKeys.ts` (every dialog), `common/Kbd.tsx` (key hints on buttons), `transactions/ItemSearchBox.tsx` + `data/itemSearch.ts` (the bill's item search). The keys are listed in `.claude/rules/popups-and-errors.md` §4 and the Shortcuts sheet; a new screen or dialog must work without a mouse.
- **Notifications and validation** follow `.claude/rules/popups-and-errors.md`: server results go to the snackbar (`Toast.tsx` / `toastStore.ts`), and client-side form mistakes are shown inline (`FormField.tsx`, and `InlineError`/`FormErrorSummary` in `FormErrorSummary.tsx`), never as toasts.
- Sales Invoice and Purchase Bill take items from `data/stockData.ts` (`useStockItems()`, loaded from `/masters/items`). A bill line holds the item's index in `STOCK_ITEMS`, so that array is only merged in place, never reordered. Call `loadStockItems()` after a save to refresh QOH. There is no sample data in the frontend either: counters, customers and sales persons come from the API, the next bill number from `GET /transactions/next-number` (a preview; the backend numbers on save), and prints show only the real data (`print/printData.ts` holds empty shapes; Print is disabled when there is nothing to print).
- Styling notes (Tailwind v4, palette, shared class strings in `lib/styles.ts`) are in `frontend/CLAUDE.md`.

## Workflow

- **Never commit credentials.** DB host/IP, port, user, password, the legacy encrypted password, and JWT secrets go only in `backend/.env` (gitignored). Code gets no defaults for them, and `.env.example` and the docs get placeholders only. `SvtConn.ini` is gitignored for the same reason. Before a commit, grep the diff for IPs and passwords.

- After changing a screen, endpoint or report, run the `parity-reviewer` agent.
