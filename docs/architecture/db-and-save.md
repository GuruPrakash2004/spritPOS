# Database, setup and save-to-SQL

Moved verbatim from `.claude/CLAUDE.md`.

- **One database: the shop's own Microsoft SQL Server, the one the desktop vLQMS uses. No SQLite, no copy.** The backend runs on the client's PC/server beside local SQL Server (often Express) and works on the desktop's **own tables directly** (`MstITEM`, `MstCUST`, `TrnHdrSINV`, `UtlStockList`, …), so desktop and web share data. `app/store.py` holds every table as a module-level dict (`ITEMS`, `CUSTOMERS`, `USERS`, `ROLES`, `SETTINGS`, `DOCS`, …), **empty until loaded** (only built-in config: roles, Global Settings definitions). On startup `app/boot.py` connects (`app/db.py`: pyodbc with ODBC Driver 18/17, then pymssql; `DB_HOST` may be `localhost\SQLEXPRESS`, `DB_PORT` optional, SQL login only, password sealed in `DB_PASSWORD_ENC`) and, once set up, `db_store.load_masters()` loads company, financial years, items, customers, suppliers, groups, brands, UOMs, packages, ledger groups, ledgers, sales counters, sales persons, last purchase dates and users; `load_transactions()` loads the latest 200 sales invoices and 100 purchase bills in a background thread; then `sqlstore.load()` lays the web app's saved data over it. `pyodbc` is installed only off macOS (`requirements.txt`), so on a Mac the connection uses pymssql (SQL logins only). The web app **writes to the live desktop tables**: back the database up before first use. Without a database there is no data and nobody can sign in (pytest installs `tests/sample_data.py` via `tests/seed.py`).
  **One-time Database setup** (`app/setup_db.py`, `routers/setup.py`, `components/auth/DatabaseSetup.jsx`): while `.env` has no database the sign-in page shows Database setup instead of login. It is open to anyone reaching the sign-in page while not set up (no setup code; a sealed password this PC can't unseal counts as not set up, `db._password_unreadable`); otherwise only an Administrator may use `/setup/*` (Global Settings → Database changes the settings in use; a blank password keeps the saved one). Exception: a set-up but offline database also allows the sign-in page's Database settings from the server PC itself (loopback request), since nobody can sign in. It tests the server, lists databases, saves the connection (`app/envfile.py` atomically writes only `DB_*` keys; password arrives encrypted for purpose `db`, stored sealed), checks it is a vLQMS database (`setup_db.REQUIRED_TABLES` and the desktop's stock trigger on `UtlStockList`), creates the web app's **five own tables** `Web_AppRow`/`Web_AppDoc`/`Web_AppMove`/`Web_AppSetting`/`Web_ToolAudit` from `migrations/web_app_tables.sql` (guarded; no desktop table is created, altered or emptied) and loads the data. Nothing is copied.

- **One DB connection, serialised.** `db.py` shares one connection between request threads and the background loader; every query runs under `_db_lock` (pymssql fails with "Unknown error" on concurrent use). New DB calls go through `db.fetchall`/`db.execute`, or `db.transaction()` for statements that must commit together (`?` placeholders for both drivers).
- **Every change is saved to SQL Server in the same request** (`app/sqlstore.py`). After a successful POST/PUT/DELETE the write middleware in `main.py` (which also runs writes one at a time) calls `sqlstore.save()`, writing what changed since the last save in ONE `db.transaction()`:
  - Rows marked with `store.touch(TABLE, key)` go to the desktop's own table (`LEGACY_MASTERS`: `MstITEM`, `MstCUST`, `MstSUPP`, `MstITEMGROUP`, `MstBrand`, `MstUOM`, `MstPKG`, `MstUser`, `MstLed`, `MstLedgroup`, `MstSC`, `MstSP`; new rows get `MAX(ID)+1`; a user's desktop `LoginPwd` is never touched) and whole to `Web_AppRow` (fields with no desktop column, e.g. password hashes; other masters, roles, rights live only there).
  - Documents without an `origin` go whole to `Web_AppDoc`; saved sales invoices / purchase bills also go to `TrnHdrSINV`/`TrnDtlSINV` and `TrnHdrPB`/`TrnDtlPB` (cancel/remove set `Cancelled`/`IsDelete`, also on bills made in the desktop).
  - `MOVEMENTS[APP_MOVEMENTS_FROM:]` go to `Web_AppMove` (the web's ledger) and each to a `UtlStockList` row, whose desktop trigger keeps `TrnQOH` (a sale cancel deletes that bill's stock rows, as the desktop does).
  - Settings and other web state → `Web_AppSetting`; audit entries → `UtlAdmAudit`/`UtlAdmAuditItem` (desktop's audit tables, so its history shows too).
  - If the transaction fails the request answers **503** and `sqlstore.reload()` reloads memory from SQL Server, so memory never keeps an unsaved change.
  - At startup item QOH comes from `TrnQOH` (includes web moves); `sqlstore.load()` takes web moves off and replays them so `store.BASE_QOH` stays right for Re Write Stock, and moves the invoice series past the highest `SINVNO`.
  - **A new write must call `store.touch()`** for any master/user/role row it changes, and new documents must live in `store.DOCS`, or the change is not saved.
  - Merge Items calls `sqlstore.merged(src, dst)`, which re-points every table's ITEMID and adds the two `TrnQOH` rows.
  - Saves with an `Idempotency-Key` header (Sales Invoice and Purchase Bill send one per draft) are answered from `store.IDEMPOTENT` when repeated with the same body (different body → 409): a double-click makes one bill.
  - Uploaded company files live in `backend/uploads/company/`.
