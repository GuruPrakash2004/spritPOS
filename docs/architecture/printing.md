# Printing through the Crystal bridge

Moved verbatim from `.claude/CLAUDE.md`.

- `print/`: **documents print through their original Crystal `.rpt` files**, as the desktop does. `PrintDialog.jsx` + `lib/printing.js` read print options from `GET /print/options` (Doc Designer's `UtlOption`: default option, click actions, after-save prompt; `backend/app/designer.py`) and ask `POST /print/render` for the PDF. Each option says whether its `.rpt` is in the report folder (`available`); the user's last pick is kept on the server (`PUT /print/preference`, `store.PRINT_PREFS`) and beats the designer's default. `app/rpt_print.py` builds the job like `frmUtlReportViewer` (file, selection formula, parameters) and `app/rpt_bridge.py` has the Crystal Reports bridge (`backend/tools/rptbridge/`, Windows) lay it out. **The backend only builds a job and calls a print service over HTTP** (`POST /render` → PDF, `POST /print` → printer; it never opens a `.rpt`). Two services speak that contract: the real Crystal one (`tools/rptbridge/bin/RptBridge.exe`, Windows) and the built-in `app/mock_bridge.py` (HTML/Jinja2 templates picked by `.rpt` name, PyMuPDF Story; layout is ours, not the desktop's; formats without a template answer 501, direct printing 409). Prefer the real bridge when Crystal's exact layout matters.
    - **Nothing has to be set**: on Windows with the exe present, `app/bridge_launcher.py` (from `main.py` startup/shutdown) runs it on 127.0.0.1:8765 with `RPT_BRIDGE_KEY` or a key made up at each start, restarts it whenever it exits, replaces a leftover bridge that refuses the made-up key (never when `RPT_BRIDGE_KEY` is set), and stops it with the backend. It runs as the backend's Windows user, so a service that direct-prints to a network printer must run as a user who has it. Without the exe (Mac/Linux, or not built) the built-in print answers. `RPT_BRIDGE_URL`/`RPT_BRIDGE_KEY` are for a bridge you run yourself; `RPT_BRIDGE_AUTOSTART=0` turns autostart off; otherwise only `RPT_FOLDER` (the `.rpt` path, default `backend/Rpts`, editable from the sign-in page's Database & report settings and Print Settings via `/setup/rpt-folder`) is a setting. A new report format needs a template in `mock_bridge.py` for the built-in print.
    - **Filling a format's shop details (real bridge):** every job carries the shop's details under common parameter names (`rpt_bridge.company_parameters`: CompName, Phone/phno, Email, GSTIN, Add1..4; the job's own parameters win; the bridge skips names a report doesn't define), `label_values` (`LABEL_FIELDS`: a text object holding only a label such as PH NO: / Email ID: / GSTIN No: gets the value after it) and `address_lines` (MstComp Address1..4: a wide blank spaces-only text object above the first filled label is the address). `FillLabels` in `tools/rptbridge/Program.cs` does it when the report opens, so preview, export and direct print all get it, and no format is special-cased by object name. Rebuild `RptBridge.exe` after changing Program.cs: `dotnet build -c Release -p:CrystalDir=<folder with the CrystalDecisions DLLs>`. A new label wording is one entry in `LABEL_FIELDS`. `rpt_bridge.friendly_error` rewrites Crystal's RPC / printer errors into plain advice.
    - **Report prints (DSR, Stock Balance, Customised Reports) still use the old `PrintFormatSelectorModal.jsx` / `rptRegistry.js` / `layouts/*`, which are not derived from the `.rpt` files** (don't describe them as matching legacy prints); they are to move to the bridge (see `LEGACY_PARITY.md`).
