# Printing through the Crystal bridge

Moved verbatim from `.claude/CLAUDE.md`.

- `print/`: **documents print through their original Crystal `.rpt` files**, as the desktop does. `PrintDialog.jsx` + `lib/printing.js` read print options from `GET /print/options` (Doc Designer's `UtlOption`: default option, click actions, after-save prompt; `backend/app/designer.py`) and ask `POST /print/render` for the PDF. Each option says whether its `.rpt` is in the report folder (`available`); the user's last pick is kept on the server (`PUT /print/preference`, `store.PRINT_PREFS`) and beats the designer's default. `app/rpt_print.py` builds the job like `frmUtlReportViewer` (file, selection formula, parameters) and `app/rpt_bridge.py` has the Crystal Reports bridge (`backend/tools/rptbridge/`, Windows) lay it out. **The backend only builds a job and calls a print service over HTTP** (`POST /render` → PDF, `POST /print` → printer; it never opens a `.rpt`). Two services speak that contract: the real Crystal one (`tools/rptbridge/bin/RptBridge.exe`, Windows) and the built-in `app/mock_bridge.py` (HTML/Jinja2 templates picked by `.rpt` name, PyMuPDF Story; layout is ours, not the desktop's; formats without a template answer 501, direct printing 409). Prefer the real bridge when Crystal's exact layout matters.
    - **Nothing has to be set**: on Windows with the exe present, `app/bridge_launcher.py` (from `main.py` startup/shutdown) runs it on 127.0.0.1:8765 with `RPT_BRIDGE_KEY` or a key made up at each start, restarts it whenever it exits, replaces a leftover bridge that refuses the made-up key (never when `RPT_BRIDGE_KEY` is set), and stops it with the backend. It runs as the backend's Windows user, so a service that direct-prints to a network printer must run as a user who has it. Without the exe (Mac/Linux, or not built) the built-in print answers. `RPT_BRIDGE_URL`/`RPT_BRIDGE_KEY` are for a bridge you run yourself; `RPT_BRIDGE_AUTOSTART=0` turns autostart off; otherwise only `RPT_FOLDER` (the `.rpt` path, default `backend/Rpts`, editable from the sign-in page's Database & report settings and Print Settings via `/setup/rpt-folder`) is a setting. A new report format needs a template in `mock_bridge.py` for the built-in print.
    - **Filling a format's shop details (real bridge):** every job carries the shop's details under common parameter names (`rpt_bridge.company_parameters`: CompName, Phone/phno, Email, GSTIN, Add1..4; the job's own parameters win; the bridge skips names a report doesn't define), `label_values` (`LABEL_FIELDS`: a text object holding only a label such as PH NO: / Email ID: / GSTIN No: gets the value after it) and `address_lines` (MstComp Address1..4: a wide blank spaces-only text object above the first filled label is the address). `FillLabels` in `tools/rptbridge/Program.cs` does it when the report opens, so preview, export and direct print all get it, and no format is special-cased by object name. Rebuild `RptBridge.exe` after changing Program.cs: `dotnet build -c Release -p:CrystalDir=<folder with the CrystalDecisions DLLs>`. A new label wording is one entry in `LABEL_FIELDS`. `rpt_bridge.friendly_error` rewrites Crystal's RPC / printer errors into plain advice.
    - **Printing on the counter PC's own printers (Print Agent):** a browser can't list or use the printers of the PC it runs on, so `backend/tools/printagent/` is a small Windows program installed on each counter PC (`install.cmd`; loopback `127.0.0.1:8766`, only the web addresses in its `printagent.txt` may use it). The server draws the report as page pictures (`POST /print/pages`, PyMuPDF at 203 dpi, same layout as the preview) and `frontend/src/lib/localPrint.js` sends them to the agent, which prints on that PC's printer. `PrintDialog.jsx` lists **This PC** printers (value `pc:Name`, the PC's default first, or the one last picked) beside the server's; `runPrint` / `afterSavePlan` (`lib/printing.js`) send a Save & Print direct print to this PC's default printer when the agent runs. Without the agent everything works as before (server printers, browser Print). The backend builds the agent at startup when it is missing (`main._prepare_print_agent`, .NET Framework `csc.exe` on a Windows server) and serves it from `GET /print/agent?origin=` as ONE self-installing `.cmd` (the exe inside, set to the page's address); the Print window offers it and finds the agent by itself after setup. Details: `backend/tools/printagent/README.md`.
    - **Report prints (DSR, Stock Balance, Customised Reports) still use the old `PrintFormatSelectorModal.jsx` / `rptRegistry.js` / `layouts/*`, which are not derived from the `.rpt` files** (don't describe them as matching legacy prints); they are to move to the bridge (see `LEGACY_PARITY.md`).

## The bridge's slow first start (found 2026-11-18)
- On some PCs the **first call into Windows' printing system in a new process takes 50 to 160 s** (measured with `System.Drawing.PrinterSettings`; every later call takes ~0.2 s). Probable trigger: a printer that is offline or unreachable, such as a network printer on another PC. Crystal makes that call inside `ReportDocument.Load`, so the first report of every new bridge outlived the bridge's 55 s limit, was killed, and the restart paid the same again (the log showed `load start X` with no `load done X`).
- `tools/rptbridge/Program.cs` now pays that cost once, in the background, at start-up (`Prewarm`). `/health` answers at once with `ready: false` until then; report requests wait for it (up to 240 s) and the 55 s limit counts only after it. Reports then open in 0.5 to 1.1 s and reopen in about 0.3 s.
- `bridge_launcher.py` waits for `ready` before warming (`_ready`, `wait_ready`), warms one report per `/warm` call, and `rpt_bridge._call_once` waits for a restarting bridge. The key is kept in `backend/data/bridge.key` so a bridge that is still running is reused after a backend restart; `RPT_BRIDGE_KEEP_ALIVE=1` leaves the bridge running when the backend stops (otherwise a restart costs the slow start again).
- Stage lines go to `backend/data/bridge.log`. The cure on the PC itself is to remove the dead printer (Windows Settings > Printers).
- The Print window does NOT cache finished PDFs (a short-lived cache keyed by format showed an old label list; `components/print/usePdfPreview.test.jsx` guards it).
- **Long shop addresses (2026-11-18):** the sales invoice format prints the address as ONE text object, `{?Add1} {?Add2} {?Add3} {?Add4}`, one line tall, with the "PH NO:" line a fixed distance below it (room for two lines). A shop whose address needs three lines printed the extra line on top of "PH NO:" (it looked like two lines printed over each other). `MakeRoom` in `tools/rptbridge/Program.cs` measures any text object holding `{?...}` placeholders with its own font and width, moves the objects below it down by the missing height and sets the section to its old height plus that. A kept (reused) report is put back to its saved positions and heights before each job. Nothing changes when the text already fits. `POST /describe` on the bridge lists a report's sections and objects (position, size, what they show) to investigate a layout.
- `MakeRoom` also covers `fmtPB.rpt` (purchase bill: `{?Add1}{?Add2}{?Add3}` with "Phone No" below it). Horizontal lines in the moved section (a divider under the header) are moved through a vertical state (`MoveTo`): Crystal refuses to change one coordinate of a line ("Only vertical or horizontal lines are supported"), and a kept report's lines are put back the same way. Not yet looked at: `fmtExp`, `fmtPSE`, `fmtSTKDED*`, `fmtSPInvPrint_*`.
- **Labels (`RPTBC.rpt`) failed with "Selected exporter does not support one of the features used in this report" (2026-11-18).** The label's barcode is a formula (`'*' + UpperCase({RptBC.ItemCode}) + '*'`) drawn in the font `svtBarcode`, installed from an OpenType (CFF) file (`svtBarcode-Regular.otf`, per user). Crystal's PDF exporter can't embed an OpenType font. When a PDF export fails like that, the bridge (`SwapOpenTypeFonts` in `Program.cs`) finds the report's fonts installed from `.otf` files (registry list under `...\Windows NT\CurrentVersion\Fonts`, both hives) and retries with TrueType stand-ins: a barcode-named font becomes `Code39AzaleaRegular1` (or another installed TrueType Code 39 font) at 85% size, any other becomes Arial. `RPT_FONT_MAP="svtBarcode=SomeFont;Other=Arial"` in the bridge's environment overrides it. A direct print (`PrintToPrinter`) uses the original fonts. Installing a TrueType build of the barcode font on the PC is the cure that keeps the original look. The web page sends `{code, copies, qty, mrp, barcode}`; `app/rpt_barcode.py` writes them to `RptBC` under a `WEB-<user>` tag, numbers `Slno` after the table's highest (PK_RptBC is on Slno alone) and removes the rows afterwards.
- **Labels stack top to bottom.** `RPTBC.rpt` is a multi-column label sheet (four labels across, then down). `app/rpt_barcode.py` sends `"columns": 1` and the bridge's `StackColumns` narrows the printable width to the Detail section's width plus 300 twips, so only one column fits and the labels follow each other down the page. The .rpt itself is not changed; a job without `columns` prints as designed.
